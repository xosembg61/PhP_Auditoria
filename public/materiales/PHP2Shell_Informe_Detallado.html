1. Dónde está realmente el fallo

Separar frontend, aplicación e intérprete antes de decidir qué actualizar.

Explicación sencilla

PHP ejecuta el backend. Si falla el intérprete, actualizar solo Angular o Laravel deja esa pieza sin comprobar.

Modelo mental: Piensa en una receta y en la cocina donde se prepara. Cambiar la receta no repara automáticamente un equipo defectuoso de la cocina.

Límite de la analogía: Es una comparación didáctica: una vulnerabilidad de memoria depende de rutas técnicas concretas, no de que toda petición falle.

Detalles técnicos

Angular se ejecuta habitualmente en el navegador; Laravel depende de PHP en el backend. Hay otras aplicaciones PHP que también deben inventariarse.

El impacto de un fallo del intérprete depende de la versión, el paquete y las condiciones alcanzables. Usar PHP no demuestra compromiso.

Cómo trabajar el paso

  1. Dibuja el recorrido de una petición

    Navegador → Angular → API HTTP → Laravel/PHP → servicios internos. Añade otras aplicaciones PHP conocidas.

    Buscar: Un mapa que diferencie código de aplicación y runtime.

    Documentar: Arquitectura conceptual; marca como desconocido lo que no esté verificado.

  2. Localiza la pieza que corrige el fallo

    Consulta quién mantiene PHP y cómo se instala en ese entorno.

    Buscar: Un paquete del sistema, una imagen, una instalación del proveedor o una compilación propia.

    Documentar: Origen del runtime y función responsable.

  3. Evita un cierre prematuro

    Pregunta por separado si se actualizó el framework y si se corrigió el intérprete.

    Buscar: Dos actuaciones distintas, con registros distintos.

    Documentar: Lo que se conoce, lo que se supone y lo que falta comprobar.

Mapa conceptual, no inventario de Twinteach

Frontend: Angular
Backend: Laravel sobre PHP
Runtime web: pendiente de identificar
Estado de parche: no verificado

Interpretación: La arquitectura orienta dónde buscar; todavía no acredita una versión ni un parche.

No demuestra: No demuestra vulnerabilidad explotable ni intrusión.

Errores frecuentes

  • El frontend está actualizado, así que PHP2Shell está resuelto. Falta verificar PHP en el backend y el resto de servicios que lo ejecutan.
  • Todas las webs PHP han sido atacadas con éxito. Exposición, posibilidad técnica, intento observado y compromiso son hechos distintos.

    • Fuentes: PHP · PHP Manual

2. Encontrar el PHP que sirve la web

No confundir una salida de consola con una comprobación del servicio HTTP.

Explicación sencilla

Puede haber varios PHP en el mismo servidor. La consola, PHP-FPM, Apache y un contenedor no tienen por qué compartir versión o configuración.

Modelo mental: La etiqueta de un ordenador del aula no identifica todos los ordenadores del edificio. Primero relaciona cada servicio con su equipo.

Límite de la analogía: Un proceso puede estar dentro de un contenedor o gestionado por un proveedor: el inventario debe reflejar esa arquitectura real.

Detalles técnicos

SAPI es la interfaz de integración de PHP. CLI se usa desde consola; FPM gestiona procesos que reciben trabajo del servidor web.

Los pools FPM pueden tener configuraciones distintas. Un comando de consola muestra su propia configuración, no la de todos los servicios.

Cómo trabajar el paso

  1. Relaciona la aplicación con su servicio

    Consulta el panel, el inventario o el despliegue autorizado. Identifica pool, módulo, contenedor o servicio gestionado.

    Buscar: La relación concreta entre la aplicación y su runtime web.

    Documentar: Entorno, SAPI, proveedor y fecha.

  2. Usa la consola como dato auxiliar

    Si tienes acceso autorizado, consulta php -v y php --ini. Esta web solo los muestra: no ejecuta comandos.

    Buscar: Versión CLI y archivos de configuración de CLI.

    Documentar: Etiqueta expresamente el resultado como CLI.

  3. Pide la comprobación del runtime web

    Contrasta el paquete y la configuración del proceso que atiende HTTP con el administrador.

    Buscar: Una evidencia específica del servicio, no una suposición por coincidencia de nombres.

    Documentar: Paquete efectivo, versión, SAPI y referencia administrativa.

Salida sintética de consola

php -v
php --ini
PHP 8.3.36 (cli) [SALIDA FICTICIA]
Loaded Configuration File: /ruta-de-ejemplo/php.ini

Interpretación: La consola del ejemplo utiliza esa versión y ese archivo.

No demuestra: No prueba que PHP-FPM, Apache o las réplicas usen esa misma versión. No publiques un phpinfo() accesible por Internet.

Errores frecuentes

  • php -v muestra una versión corregida: todo el servidor está actualizado. Comprueba el runtime HTTP, workers y otras instancias por separado.
  • FPM utiliza siempre la misma configuración que CLI. Identifica su pool y configuración efectiva.

    • Fuentes: PHP Manual · PHP Manual · PHP Manual

3. Leer versiones sin caer en falsos positivos

Distinguir un mínimo upstream de una revisión de paquete del proveedor.

Explicación sencilla

El número base de PHP no cuenta toda la historia. Una distribución puede incorporar el parche sin cambiar a la primera versión corregida publicada por PHP.

Modelo mental: Un libro puede conservar el número de edición y llevar una fe de erratas incorporada. Necesitas identificar la revisión exacta y quién la publicó.

Límite de la analogía: No basta con afirmar que puede haber un backport: hay que acreditar que el paquete instalado lo contiene y que el servicio lo está usando.

Detalles técnicos

Upstream identifica publicaciones del proyecto PHP. Los paquetes de distribución añaden revisiones y pueden retroportar correcciones.

Para paquetes del proveedor, compara distribución, release, repositorio, nombre y revisión exacta. Los estados del proveedor no se trasladan a un PPA o una imagen ajena.

Cómo trabajar el paso

  1. Identifica el tipo de versión

    Distingue una versión upstream como 8.3.36 de una cadena de paquete que incluye una revisión del proveedor.

    Buscar: La cadena completa, sin recortar sufijos para obtener un resultado favorable.

    Documentar: Versión completa y procedencia.

  2. Consulta los dos CVE

    Busca la distribución y el paquete exactos en los avisos oficiales del proveedor.

    Buscar: Una corrección documentada para ambos CVE iniciales.

    Documentar: Enlaces, release y revisión corregida consultada.

  3. Cierra el salto entre documento y servidor

    Confirma que esa revisión está instalada y cargada por el servicio web. Revisa por separado el seguimiento del 23 de octubre.

    Buscar: Comprobación posterior del runtime efectivo.

    Documentar: Fecha, servicio y evidencia de uso del paquete.

Referencia oficial de Ubuntu consultada el 26/10/2026

Distribución: Ubuntu 22.04 LTS (jammy)
Paquete fuente: php8.1
Revisión indicada como corregida para los dos CVE iniciales:
8.1.2-1ubuntu2.28

Interpretación: Las fichas oficiales de Ubuntu registran una corrección del proveedor con número base 8.1.2.

No demuestra: No clasifica cualquier 8.1.2 como corregido, no acredita el estado de Twinteach y no resuelve por sí solo el seguimiento de sesiones del día 23.

Errores frecuentes

  • Toda versión 8.1.2 carece necesariamente de parche. El soporte upstream y la revisión corregida de un proveedor son preguntas diferentes.
  • Puede haber un backport, así que lo doy por aplicado. Sin revisión exacta y aviso correspondiente, el estado sigue sin comprobar.

4. Aplicar una corrección y comprobarla

Entender qué debe cambiar y qué evidencia permite cerrar la actualización.

Explicación sencilla

Instalar el paquete es una parte del trabajo. También hay que renovar los procesos pertinentes, revisar otras instancias y verificar el servicio después del cambio.

Modelo mental: Cambiar una pieza en el almacén no demuestra que todos los equipos estén utilizando la pieza nueva.

Límite de la analogía: El procedimiento concreto depende de distribución, alojamiento, contenedores y continuidad del servicio. No hay un comando universal válido para todos.

Detalles técnicos

La remediación debe seguir el procedimiento del proveedor y un cambio autorizado. Los procesos de larga duración requieren atención específica.

El seguimiento del 23 de octubre de PHP trata un vector poco habitual ligado al progreso de subidas y cambios del serializador de sesión durante la ejecución. Consulta sus condiciones antes de cerrar la revisión.

Cómo trabajar el paso

  1. Preparar el cambio con el responsable

    Identifica versiones, origen del paquete, compatibilidad, respaldo y procedimiento de recuperación.

    Buscar: Un plan de cambio aprobado para ese entorno.

    Documentar: Alcance y función responsable, sin inventar personas.

  2. Actualizar todos los elementos del inventario

    El administrador aplica la corrección del proveedor. En contenedores, revisa imagen base, reconstrucción y despliegue de todas las réplicas.

    Buscar: Paquete o imagen corregidos con referencia trazable.

    Documentar: Registro del cambio y lista de instancias cubiertas.

  3. Validar la carga del código corregido

    Comprueba que los workers o servicios pertinentes se renovaron y que el runtime efectivo corresponde al paquete esperado.

    Buscar: Evidencia posterior al cambio y revisión de errores funcionales.

    Documentar: Hora, comprobación y entornos que sigan pendientes.

  4. Revisar el seguimiento oficial

    Consulta el aviso del día 23 y confirma con el responsable si la configuración y el código afectados existen en el entorno.

    Buscar: Una respuesta documentada, no una conclusión basada solo en el número de versión.

    Documentar: Condiciones revisadas y medida correspondiente.

Registro de cambio ficticio

DEMO · Cambio CHG-EJEMPLO
Paquete corregido: referencia pendiente de adjuntar
Workers renovados: documentado en registro del servicio
Runtime HTTP posterior: pendiente de comprobar
Resultado: actualización todavía en revisión

Interpretación: La instalación y la renovación están registradas, pero queda una comprobación relevante.

No demuestra: No corresponde a Twinteach y no debe marcarse como cierre completo hasta aportar la evidencia restante.

Errores frecuentes

  • Un WAF equivale al parche. Puede reducir exposición a determinadas peticiones; no cambia el intérprete instalado.
  • Un cambio genérico de memory_limit sirve para cualquier instalación. Las mitigaciones tienen límites y efectos de disponibilidad; sigue la guía oficial del entorno.

5. Relacionar logs sin inventar una intrusión

Separar una anomalía, un indicio de compromiso y la atribución a una CVE.

Explicación sencilla

Un error no explica por sí solo su causa. Combina fuentes, comprueba cobertura temporal y conserva alternativas antes de concluir.

Modelo mental: Una alarma y una puerta abierta justifican revisar; no identifican por sí solas quién entró ni cómo lo hizo.

Límite de la analogía: En informática necesitas registros íntegros, tiempos comparables y evidencia independiente. Una analogía no sustituye un análisis forense.

Detalles técnicos

La web, el runtime, la aplicación y la monitorización pueden registrar partes distintas de una misma actividad. Los logs de Laravel dependen de sus canales configurados.

Incluye zona horaria, origen e identificadores de correlación cuando existan. Preserva originales bajo el procedimiento de respuesta y usa copias saneadas para compartir.

Cómo trabajar el paso

  1. Comprobar qué cubren los registros

    Lista accesos, errores del servidor/PHP, aplicación y monitorización; identifica intervalos ausentes.

    Buscar: Cobertura real, retención y zona horaria por fuente.

    Documentar: Qué puedes investigar y qué no.

  2. Relacionar eventos y alternativas

    Ordena peticiones, errores y reinicios. Contrasta tareas programadas, cambios autorizados y fallos operativos.

    Buscar: Coincidencia temporal y respaldos independientes.

    Documentar: Hechos observados y explicaciones alternativas.

  3. Escalar sin atribuir antes de tiempo

    Si aparecen procesos no autorizados o cambios inesperados, involucra al equipo responsable y preserva evidencia.

    Buscar: Un alcance y una causa por confirmar.

    Documentar: Grado de certeza, límites y siguiente acción.

Fragmento sintético de entrenamiento

10:31:14 UTC · WEB · petición atípica
10:31:15 UTC · PHP · worker reiniciado
10:31:18 UTC · MON · alerta de correlación

Interpretación: Hay una relación temporal que merece investigación.

No demuestra: No demuestra RCE ni identifica PHP2Shell. La ausencia de más eventos tampoco descarta intrusión si la cobertura es parcial.

Errores frecuentes

  • No hay eventos en laravel.log: no hubo ataque. Puede haber otros canales, huecos de cobertura o errores previos a la aplicación.
  • Un HTTP 500 confirma la CVE utilizada. El código HTTP no identifica la causa ni la técnica de entrada.

6. Convertir los datos en un informe útil

Entregar una conclusión que permita decidir y que otra persona pueda contrastar.

Explicación sencilla

Un informe separa alcance, hechos, incertidumbres y acciones. La seguridad no se resume con el porcentaje de casillas.

Modelo mental: Un parte de revisión dice qué se miró, con qué resultado y qué falta; una pegatina verde sin respaldo no permite reconstruir el trabajo.

Límite de la analogía: Un informe describe la evidencia disponible en un momento concreto. No garantiza el estado futuro del sistema.

Detalles técnicos

Relaciona cada afirmación con una evidencia fechada y un activo del inventario. Registra dependencias: paquete, runtime efectivo y estado de los procesos.

Las conclusiones de parche y de investigación son independientes: un servicio puede estar corregido hoy y conservar indicios de una intrusión anterior.

Cómo trabajar el paso

  1. Definir el alcance

    Indica entornos, servicios, fechas, fuentes y limitaciones de acceso.

    Buscar: Una revisión acotada que no afirme cubrir lo que quedó fuera.

    Documentar: Responsable por función y fecha de revisión.

  2. Redactar dos conclusiones separadas

    Explica el estado del parche y, por separado, los hallazgos de actividad.

    Buscar: Evidencias que respalden cada conclusión y límites explícitos.

    Documentar: Pendiente, comprobado o investigando, con el motivo.

  3. Priorizar acciones

    Propón siguiente acción, función responsable y plazo por acordar, atendiendo al riesgo real.

    Buscar: Trabajo concreto que reduzca la incertidumbre o la exposición.

    Documentar: Qué hará falta para dar la acción por cerrada.

Conclusión ficticia, limitada y revisable

DEMO · Solo se ha revisado el runtime de pruebas.
Parche: paquete documentado; producción pendiente de verificar.
Actividad: sin indicios en las fuentes revisadas, con un hueco temporal.
Siguiente acción: solicitar inventario y cobertura de producción.

Interpretación: La conclusión explica su alcance y evita generalizar a todo el sistema.

No demuestra: No certifica Twinteach ni descarta un ataque en periodos o entornos no revisados.

Errores frecuentes

  • 18 casillas marcadas equivalen a 100 % de seguridad. Miden documentación de tareas; las conclusiones dependen de su evidencia y alcance.
  • Parcheado hoy significa que nunca hubo compromiso. Remediación e investigación histórica son preguntas distintas.

    • Fuentes: PHP · php/php-src · GitHub Security · OWASP Cheat Sheet Series

Ejercicios resueltos

Una captura de consola

Una persona aporta «PHP 8.3.36 (cli)» y afirma que toda la aplicación web está corregida.

Pregunta: ¿Es suficiente para cerrar la comprobación del runtime web?

Interpretación: Acredita un dato de CLI, no el proceso que atiende HTTP. Pide SAPI, paquete del servicio web y comprobación posterior.

Una referencia de backport

En un ejercicio ficticio se aporta la revisión exacta de paquete, su release y los dos avisos oficiales del proveedor. Falta saber si el servicio usa ya ese paquete.

Pregunta: ¿Puede cerrarse toda la actualización con estos documentos?

Interpretación: La referencia del proveedor respalda el contenido del paquete; todavía falta demostrar instalación y uso efectivo en el servicio.

Una conclusión con límites

El informe de ejemplo identifica registros y ventana revisados, reconoce un día sin cobertura y concluye «sin indicios en los datos analizados».

Pregunta: ¿Es razonable como conclusión limitada a esas fuentes?

Interpretación: Sí, porque declara el alcance y el hueco. No sería válido convertirla en «no hubo intrusión».

El panel del WAF está verde

La única evidencia es una captura del WAF sin alertas. No se conoce el paquete PHP ni la cobertura de los logs.

Pregunta: ¿Eso acredita que el intérprete tiene el parche?

Interpretación: El panel no identifica qué código PHP está en uso. Consulta el runtime y al proveedor; la ausencia de alertas tiene límites.
